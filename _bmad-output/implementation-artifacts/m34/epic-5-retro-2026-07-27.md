# M34 Epic 5 Retrospective - Professional Control Drawing Closeout

Date: 2026-07-27

## Scope Reviewed

This retrospective covers M34 Epic 5: closing the professional control drawing gap.

Reviewed stories:

- Story 5.1: Freeze the professional drawing product contract
- Story 5.2: Model functions and deterministic drawing placement
- Story 5.3: Compile the rolling-shutter IEC package and semantic sample
- Story 5.4: Compose and route the professional control drawing
- Story 5.5: Prove, polish, and hand off M34

Status truth: all Epic 5 stories are in `review`, not `done`. This is a closeout retrospective for the
implemented and verified product proof, not a final release declaration.

## What Worked

- The team corrected the M33 architecture mistake instead of hardening it. Runtime XML package
  authority was removed from the active product path.
- Athena source became the single metadata authority for symbols, elements, profiles, bindings,
  engineering functions, placement, and package-local material.
- The final product target was narrowed to one visible surface: `Control Drawing`, backed by the
  existing `schematic` projection. This avoided the earlier problem of three weak views competing in
  the workbench.
- The proof became structured and falsifiable. The final E2E payload proves exact counts:
  22 graphic occurrences, 34 semantic routes, 62 terminal bindings, 36 drawing-layer items,
  17 columns, 8 rows, zero legacy representation facts, and zero route body intersections.
- The mandatory polish/purge rule paid off. Generated snapshots, stale M33 examples, M33 IEC runtime
  fixtures, and dead `start:m33` scripts were removed from active workspace paths.

## What Did Not Work

- The milestone initially tried to keep too many surfaces alive: Cabinet, Documentation, and
  Schematic. That diluted quality and produced a confusing product surface.
- XML and runtime package manifests were a wrong boundary for Athena. They created a second source of
  truth and undermined the compiler architecture.
- Visual ambition exceeded the representation model at first. The QET screenshot target revealed that
  professional output requires language, semantic function modeling, package material, placement,
  routing, composition, and renderer changes together.
- Generated `.athena/snapshots` kept reappearing during verification. They are useful cache output but
  must remain non-source and be purged after proof runs.
- The final drawing is credible but still not a full QET/EPLAN/IEC-equivalent professional drawing
  engine. We must keep that boundary explicit.

## Key Lessons

1. Focus beats breadth. One product surface at high quality is better than three incomplete views.
2. Athena metadata must have one authority. SVG can carry geometry and local node markers, but Athena
   source owns identity, role, compatibility, version, policy, and binding.
3. Vendor/reference material is evidence and input, not architecture. QET is useful for visual/domain
   learning, but no QET runtime model should leak into Athena.
4. Professional rendering is not frontend polish. It needs upstream typed concepts: functions,
   terminal anchors, explicit placement, representation material, composition facts, and route facts.
5. Every story needs a final purge gate. Without it, dead code, stale docs, generated caches, and
   obsolete scripts accumulate quickly.

## Architecture Outcome

Accepted active path:

```text
Athena project source
  -> engineering semantic model
  -> typed functions and explicit placement facts
  -> Athena representation material resolution
  -> professional drawing compiler
  -> drawing composition and route facts
  -> typed Presentation/LSP payload
  -> paint-only Theia Control Drawing
```

Rejected active paths:

- XML package manifests as runtime authority
- QET `.elmt` or `.qet` runtime loading
- renderer-side engineering inference
- frontend-selected symbols/material
- fake drawing-structure devices
- broad view selector competition for M34 proof

## Remaining Risks

- Stories are in `review`, so an independent review still has to mark them `done`.
- The product proof is structured and real, but not pixel-perfect against the QET screenshot.
- The language now has more representation vocabulary; future work must prevent it from becoming
  another verbose graphics XML.
- Snapshot generation needs a clear non-source lifecycle so future agents do not commit cache output.
- M35/M36 planning must avoid re-expanding to Cabinet/Documentation/Schematic before the one focused
  drawing path is strong.

## Closeout Summary

M34 Epic 5 corrected the architecture and produced a verified professional Athena-governed control
drawing proof. The major achievement is not pixel-perfect rendering; it is the corrected compiler
pipeline from Athena source to typed material, composition, routing, and paint-only presentation.

The milestone is ready for independent review. It should not be described as full IEC compliance,
EPLAN equivalence, QET compatibility, or a finished multi-view product.
